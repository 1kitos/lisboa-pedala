# ADR-005: Persistência em memória

**Estado:** revisto (substituiu decisão de SQLite)

## Contexto

### Decisão original (SQLite)
A decisão inicial era usar SQLite. O enunciado permite SQLite
ou memória. SQLite parecia a escolha natural por sobreviver
a restarts e ser fácil de operar.

### Problema identificado
O enunciado diz explicitamente "persistência em SQLite ou em
memória". Com 6 pessoas, orçamento fixo e um protótipo
funcional, o setup de SQLite (schema, migrações, conexões,
WAL mode) adiciona complexidade sem benefício real para o
âmbito do trabalho. A US-3 (reenvio offline sem duplicar) não
precisa de persistência entre restarts — precisa de
deduplicação dentro de uma sessão, que um `set` Python garante.

## Decisão revista

Persistência em dicionários Python em memória por componente
(module-level). Cada `service.py` tem os seus próprios dicts
no topo do ficheiro. Os dados não sobrevivem a um restart —
aceitável para um protótipo.

## Consequências

- **Positivas:** zero setup, zero dependências externas, testes
  simples (sem fixtures de base de dados), código mais limpo.
- **Negativas:** dados perdem-se num restart; não é adequado
  para produção.

## Alternativas rejeitadas

- **SQLite:** overhead de setup desnecessário para o âmbito
  do protótipo; requer gestão de schema e conexões.
- **PostgreSQL:** ainda mais overhead; fora de âmbito.
